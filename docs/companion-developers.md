# Companion: developer notes

The companion is the backend a Family phone talks to when there is no Home Assistant. It is deliberately small and backend-neutral so that a Home Assistant implementation can follow the same protocol later.

## Layout (under `companion/`)

| Path | What |
|---|---|
| `worker/src/worker.js` | front door: static parent page, phone routes (signed) and parent routes (bearer key) |
| `worker/src/family.js` | Durable Object `Family` (SQLite): pairings, devices, sync, parent actions |
| `worker/src/hub/` | the Home Assistant hub ported to JavaScript: `schedule.js` (settings to phone config), `hub.js` (parent actions, sync merging), `power.js`, `store.js` |
| `worker/src/crypto.js`, `seal.js` | WebCrypto helpers; sealed credentials |
| `worker/src/page/` | parent page (vanilla JS): `app.js` (shell), `phone.js` (one phone's controls), `track-view.js` and `track.js` (location history map and playback maths), `ui.js`, `timetable.js`, `spotify.js`, `enrol.js`, `look-options.js`, `guide.html` |
| `worker/schema/profile.schema.json` | the profile document (JSON Schema); validated in the Worker with precompiled Ajv code |
| `worker/PROTOCOL-DRAFT.md` | pairing, sync, QR and typed-code formats, sealed secrets |
| `worker/test/` | `vectors.json` (shared test vectors for any client or backend) and the test suites |
| `setup-tool/` | local setup page, REST deploy engine (no wrangler needed) |

## Build and test

```bash
cd companion/worker && npm install
node scripts/build-page.mjs        # regenerate src/page-assets.js after editing src/page/*
rm -rf .wrangler/state && npm run dev &     # local Worker on :8787
npm test                            # vectors, timetable, schedule, hub, track, spotify, enrol, protocol (protocol needs the dev server)
cd ../setup-tool && npm run bootstrap && npm test
```

`vectors.json` is generated by `npm run vectors`; keys are reused so published example values stay stable. Any phone client or alternative backend must reproduce the match number, the key pin, the QR fingerprint and the sealed-secret vector.

## Design points worth knowing

* **Trust:** phone and server sign every message (ECDSA P-256), with replay counters and nonce echo. Pairing needs the single-use token plus a two-sided 4-digit confirmation typed by the parent.
* **No secrets in the backend:** connector secrets are sealed in the parent's browser to the phone's key (ECDH + HKDF + AES-GCM, bound to device id and slot name).
* **Timetable:** the parent's browser resolves time zones and clock changes into absolute `segments`; the phone only follows them and falls back to the weekly `pattern`.
* **Backend port:** the HTTP API plus the schema are the whole contract, so a Home Assistant integration can implement the same endpoints.

## Keeping parity with Home Assistant

`src/hub/schedule.js` must build exactly the config the Python `schedule.py` builds. `test/golden-schedule.json` holds inputs and expected configs generated by the Python code (`python3 scripts/make-golden-schedule.py <repo>/ha > test/golden-schedule.json`); `test/schedule.test.mjs` compares them (everything except `version`, which is a different hash). When the Home Assistant side gains a setting, add a golden case, then port it. `test/hub.test.mjs` mirrors the Home Assistant hub tests for the parent actions.
