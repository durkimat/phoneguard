# Modularisation plan (draft v0.1, 2026-11-25)

Status: a guide, not a commitment. Tackle one slice at a time, each slice shippable on its own, each leaving both apps working. Nothing here is started.

## Why

- `LauncherModel.kt` (3,379 lines), `NokiaSkin.kt` (1,457) and `LauncherActivity.kt` (1,364) hold most behaviour; the `Screen` enum has 55 values. New features (media, WhatsApp screens) would add to them.
- Phone Guard (`:app`) and Family Chat (`:familychat`) already share `:wa-core`, but Family Chat has since grown its own media, sticker and rich-chat code in its app module, which Phone Guard cannot use.
- Goal: features are libraries with a small interface; the launcher is the thin place that wires them together and keeps the privileged parts (key routing, lockdown, device owner).

## Principles

1. **Split by Gradle module, not by APK.** A feature becomes its own app only if it needs a different permission set, release cadence or distribution (Family Chat is the model). See the earlier pros and cons.
2. **Pure logic first, Android second, UI last.** Rules with no Android types (like `Rich`, `WaCommands`, `StickerLibrary.search`) go in modules that unit-test on the JVM. Android-touching helpers sit in a second layer. Screens stay in the app that owns the look.
3. **A library never knows the skin.** Libraries return data (rows, bitmaps, drawables, actions). The Nokia and Mac skins and Family Chat's own UI draw it.
4. **No behaviour change in a pure extraction slice.** Move code, keep tests green, keep package names stable where possible, and ship it before building new things on it.
5. **Do not touch the key router, lockdown or `GuardService` in any slice here.**

## Target modules

| Module | Contents | Used by |
|---|---|---|
| `:wa-core` (exists) | Transport, store, message model, commands, labels | both apps |
| `:media-core` (new, JVM) | `Rich` rules (kinds, markers, captions, snippets, size, duration, fit, video limits), `StickerLibrary` index/search/recent, gallery grouping and sorting rules | both |
| `:media` (new, Android library) | `Media` (decode, animated drawable, video frame, preparePhoto, cache cleanup), `VideoPrep`, MediaStore gallery query, a dithered-or-colour renderer (from `camera/Dither.kt`) | both |
| `:media-assets` (new, optional) | the sticker library and packs (about 420 WebP files), kept out of `:media` so a build can omit them | Family Chat, Phone Guard if wanted |
| `:ui-kit` (later) | `Theme`, `Font`, dither, window and skin primitives | launcher, Family Chat |
| `:features:*` (later) | per-feature screen controllers behind a `ScreenFamily` interface: whatsapp, music, mail, calendar, where, games | `:app` |

Media screens (viewer, gallery list/grid, sticker tray) stay in the apps at first: Family Chat draws them as Material-style views, the launcher draws them through the Nokia skin. They share the data and decoding, not the pixels.

## Slices, in order

### Slice 1: media extraction (the pilot) — DONE on branch `refactor/media-modules`, uncommitted, 2026-11-25

As built: ONE module `:media` (package `io.github.durkimat.media`), not two. `Rich` reads `WaMsg`, which lives in an Android library, so a JVM-only `:media-core` could not depend on `:wa-core` anyway; the pure and Android parts stay in the same module and the pure parts are unit-tested on the JVM. Moved: `Rich`, `Media`, `StickerLibrary` (with `Sticker`), `VideoPrep`, plus `RichTest` and a new `StickerSearchTest`. `Media.cleanup` now takes the paths in use as an argument. Family Chat builds and its tests pass (`:media`, `:familychat`, `:wa-core` unit tests; release APK assembles). Gotcha for later: the sticker library `controller/familychat/src/main/assets/stickers-lib/` (13 MB) is GENERATED by `stickers/build-stickers.py` and gitignored, so a fresh worktree builds a 28 MB APK without it; the real one is 41 MB. The future `:media-assets` module needs a build step or a documented generate command.

Original plan:

Why first: it is self-contained, `Rich.kt` and `StickerLibrary` are already pure, it is needed by the new gallery and WhatsApp-media work, and a bug costs little (no lockdown or key paths).

1. Create `:media-core`; move `Rich` and the pure parts of `StickerLibrary` (`parse`, `tab`, `search`, `pushRecent`) with their tests. `Rich` depends on `WaMsg` and `WaReaction`, so `:media-core` depends on `:wa-core` for now. If that coupling bothers us, introduce a tiny `MediaItem` interface later.
2. Create `:media`; move `Media` and `VideoPrep`. One known coupling: `Media.cleanup` calls `Fc.store()`. Change it to take the set of paths in use as an argument.
3. Family Chat switches to the modules. Behaviour identical; its tests and the rc7 checklist still pass.
4. Check APK size and the Media3 dependency footprint. Phone Guard has `media3-exoplayer`; Family Chat has `media3-transformer`/`effect`. Keep `VideoPrep` in a separate `:media-transcode` module if Phone Guard should not carry the transformer.

Exit test: Family Chat released unchanged to users; no new Phone Guard behaviour yet.

### Slice 2: the gallery (first new feature on the modules) — BUILT 2026-11-25 on `refactor/media-modules`; checked in the emulator 2026-11-26 (not yet on the J36)

## Reusing Family Chat's WhatsApp features in Phone Guard

Already shared: `:wa-core` (`WaStore`, `WaMsg`, `WaTransport`, `WaCommands`) and the Go bridge AAR. Phone Guard's `WhatsApp.kt` (441 lines) already sits on it, so the foundation is common.

| Family Chat piece | Reuse in Phone Guard | Work |
|---|---|---|
| Rich rules (`Rich`) | as is, via `:media-core` | move only |
| Sticker library and tray logic | as is; tray UI redone for the keypad | UI only |
| Media decode, cache, photo prep, video prep | as is, via `:media` | move, small refactor |
| Group by id, `gid:` allowlist, admin group commands, tag-in-Send | step 3 of the familychat plan (design already sent) | in progress elsewhere |
| Edit/delete own messages, reactions, quoting | data exists; needs keypad flows (menu on a message) | UI and key design |
| Conversation and viewer screens | not reusable: touch and Material-style views | rebuild in the Nokia skin |
| Setup flow, PIN screens, Notifier, ConnectionService | partly overlap with Phone Guard's own setup and connection policy | decide: keep both, do not merge |

Principle: share the data, rules and decoding; do not share screens.

Risks to settle early:
- **Two apps, one WhatsApp account.** Both link the parent's account as linked devices; confirm each app uses its own session and cannot fight over the same store or admin group.
- **Behavioural drift.** Phone Guard's connection policy (periodic, low battery) differs from Family Chat's always-on service. Keep that policy outside the shared modules.
- **Terms and ban risk** are the same as Family Chat's README says; moving code does not change them.

## Housekeeping per slice

- Unit tests move with the code; add a test where a new seam appears.
- Update `docs/ui-architecture.md` or this file when a slice completes.
- Release app-only changes with the existing `release.sh` / `release-familychat.sh`; no image change is needed for any slice above (Slice 4 may need an emoji font in the image).
- Work in a git worktree per slice (as with `phoneguard-worktrees/pg-*`), merged to main one at a time.

## Decisions (owner, 2026-11-25)

1. No shared look between the apps (Slice 7 dropped).
2. Phone Guard carries the full sticker library. Measured: `stickers-lib` is 13 MB (424 WebP files) plus 0.5 MB for our own three packs. Phone Guard's release APK is 34 MB, so about 47 MB with stickers. Family Chat's is 41 MB. As a system app it lives in the image's system partition, so check free space there when it is added.
3. A bigger image is acceptable. Expected cost: the stickers above, about 13 MB. Emoji font: the trim list in `docs/image-trim.md` removes no fonts, and Lineage normally ships a colour emoji font, so extra size is probably nil. Not verified on the device. Check with `adb shell ls -l /system/fonts | grep -i emoji`; if missing, allow roughly 10 MB more.
4. No restriction on who sends pictures to the child for now. A per-mode media switch still exists as a parent control but defaults to allowed.

## Open: the supervised linked parent account (WhatsApp mode 3)

Family Chat links the parent's own account as a linked device, with a WhatsApp group (`FamilyChat-<child>`) as the control channel. It works well. Phone Guard's WhatsApp setups so far are the SIM method (official app with a setup window), the smartphone method, and its own linked client with a control group that only its linked account can use. Things to think through with the companion:

- Is the parent-account mode a third WhatsApp method in the companion (`setup`: sim | smartphone | parent-linked), next to who/groups/tag settings?
- Control channel versus companion: the companion is the source of truth for modes, apps and timetable; the WhatsApp group is a quick remote. Decide which commands the group may send (groups, photos on/off, maybe mode override), and make every command go through the Worker so the companion page and the phone never disagree. This matches step 3 of the familychat plan (the command route that submits changes to the Worker).
- Who may send commands: Family Chat can allow any adult in the admin group; Phone Guard allows only the linked account. Pick one rule per mode and show it on the companion page.
- Link and unlink flows, and what the child sees when the link drops (reconnect, re-pair by the parent).
- The parent's account is exposed to ban risk; the companion page should say so where the mode is chosen.

Not yet looked at in depth: the Phone Guard Worker's `whatsapp` config and its admin-group code (`WaAdmin.kt`). A short design note should follow once the owner decides the method list.
