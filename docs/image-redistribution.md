# What stops us publishing the image (scoping, 2026-11-14)

Read-only analysis of image `ims38` (`system.img`, 2,352,816,128 bytes, ext4, Android 14, userdebug) and the build inputs. Not legal advice. Companion to [licensing.md](licensing.md).

**Update 2026-11-14 (owner's decision):** the image **is now published** as a GitHub release, [image-20261114](https://github.com/durkimat/phoneguard/releases/tag/image-20261114) (`system.img.gz` + `SHA256SUMS`), for owners of the J36 and personal use, while the TrebleDroid and Qin/MediaTek licence questions are being answered. It contains the 27 proprietary files described above. **To withdraw:** delete the release (or its assets) on GitHub Releases; copies already downloaded cannot be recalled. Release notes: [releases/image-20261114.md](releases/image-20261114.md).


## 1. Proprietary (Qin/MediaTek) files in the image

All 27 files installed are copied by the build (the input folder holds 28: one unused library is not installed) from `build/ims/proprietary` (private, never in git) and were taken from the phone's **own original Qin system image** (`system_a`, the firmware the phone shipped with, recorded in `build/ims/round1-files.txt`). Every path below is in the **stock `/system` partition (`system_a`), not `/vendor`**. `system_a` is the partition a flash overwrites, so the files must be copied off the stock phone *before* flashing.

* **Installed: 27 files, 15,305,037 bytes (about 15.3 MB) of 2,352,816,128, i.e. 0.65% of the image.** (The input folder holds 15,315,685 bytes in 28 files: `android.hardware.radio-V1-ndk.so`, 10,648 B, is there but not installed.) The build also produces precompiled boot-image files from the jars (`boot-mediatek-*.oat/.art/.vdex`, `mediatek-*.odex`), under 1 MB, derived from them.
* **Also derived from stock, already in the public repo:** `build/sepolicy/pg_mtk_telephony.te` (309 lines, generated by `build/tools/port_mtk_policy.py` from the stock system_ext policy: MediaTek property/type names and rules). Names and access rules rather than code, probably low risk, but it is derived from MediaTek's policy: **an owner decision whether to keep it public**.
* The stock firmware recorded in our notes is Android 13 (original firmware sha256 `aabb1148…5283`). Different production batches may carry different MediaTek builds: the files are checksummed in the build manifest and only those versions are known to work.
* **Looks proprietary but is not ours to worry about**, built from sources in the tree: `vendor.mediatek.hardware.radio@2.x.so` (about 8.7 MB, generated from `.hal` interface files in `vendor/interfaces`, licence of that tree not checked), `MtkInCallService` and `mtk-sms-fwk-ready` (from `device/phh/treble`).

## 2. How the files get into the image, and what a split would need

* `build.sh` copies the private folder to `vendor/phoneguard/ims/proprietary`; `ims.mk`/`Android.bp` install the apps as platform-signed priv-apps and the jars as dex-only modules; eight jars are on the boot classpath (`PRODUCT_BOOT_JARS`) and get **precompiled into the boot image** (`boot-mediatek-*.oat/.art/.vdex`).
* **Signature:** the apps are **re-signed at build with our platform key** (`certificate: "platform"`; the stock apps share a UID with the system and must match the image's system signature). A user's stock copies carry MediaTek's signature, so they cannot simply be dropped onto our image, and the user cannot re-sign them with our platform key (it is secret, [signing-keys.md](signing-keys.md)). Using public AOSP test keys instead would let anyone sign a system app, which is wrong for a child-management phone.
* **Boot classpath:** replacing the eight boot jars after flashing invalidates their precompiled boot-image files, so they cannot be a data-partition overlay; they would have to be rebuilt into the image (on the user's computer) or turned into ordinary shared libraries (a patch plus testing, not tried).
* **/system is read-only ext4.** The image is `userdebug`; `adb root` / `adb remount` should be possible in principle (not tested, and dynamic partitions need verity off or an overlay). `pg-provision.sh` (root, init service) could copy files, but a priv-app only counts in a system partition, and a normal install of a sharedUid app with the wrong signature is refused. So "pg-provision installs them from `/data/local/tmp`" does not work for the apps as they are.

## 4. Verdict on the "split image"

* **Publishing the image minus the MediaTek files is easy** (leave out `build/ims/proprietary`); the image would then have **no IMS**, so voice calls would depend on the network still offering 2G/3G (not tested; do not promise).
* **Adding the files back after flashing is not feasible today**: wrong signature (our platform key), boot-image precompilation of eight jars, read-only system. Making it work needs engineering with uncertain outcome: (a) a patch so the system accepts the stock MediaTek signature for those apps' shared UID, and (b) moving the boot jars to plain shared libraries, both then tested on the phone. A user-side assembly kit that rebuilds the image is, in practice, the same as "build it yourself".
* **Realistic options, best first:** (1) ask Qin/Duoqin (and MediaTek through them) for written permission to redistribute these 15 MB; (2) private sharing to people who own a J36 (the files then still come from that user's own firmware: copy off before flashing with `adb pull`, untested on the stock phone); (3) the research path above. Settle the TrebleDroid licence question in parallel (ask the maintainers; shipped binaries: `TrebleApp.apk`, overlays; GPL `busybox` source offer).
* **Before any public image:** decide on `pg_mtk_telephony.te`, write NOTICE/GPL source-offer text, and confirm Lineage's `NOTICE.xml.gz` ships in the image.
